# Queue trend diagnosis and correction

## Root cause and scope of reproduction

A deterministic scenario reproduces the reported visible state exactly: Day 70, 11 waiting Testing items, Stable before this fix. The user's original saved session/settings were not supplied, so this establishes the defect and a matching symptom, not that their run used these exact parameters.

The supplied sequence `2,2,3,3,4,4,5,6,6,7,8,8,9,10,11` already ended Growing before the correction. It remains Growing and is a regression case; it was not the failing sequence.

The actual defect was the confirmation gate: two successive windows both had to exceed the HIGH entry threshold. For periodic gradual growth the fitted change exceeds that threshold only every fifth day. The following window still strongly supports growth above the LOW retention threshold, but the old code reset pending confirmation to Stable. The direction could therefore never become established. This was not a sign error, stale UI cache or a queue count being mistaken for a slope.

## Complete calculation trace

1. Testing uses `DailySnapshot.WaitingForTestingCount`, the recorded end-of-day waiting queue, excluding active Testing WIP. Other queues use their existing recorded queue counts.
2. The latest ten simulated days are included by actual day number; no missing observations are filled or interpolated. Minimum history is four observations.
3. OLS is reused unchanged from `LivePerformance.Slope`: sum((day−meanDay) × (count−meanCount)) / sum((day−meanDay)^2), in items/day.
4. Fitted change = slope × (lastDay−firstDay), so ten consecutive observations span nine day intervals.
5. Residual RMS describes variation around the fitted line. Entry threshold = max(2 items, 2 × RMS). Retention threshold = max(1 item, RMS). All comparisons are strict `>` in magnitude. These are stabilization heuristics, not confidence intervals or capacity thresholds.
6. Raw classification uses the entry threshold. Stabilized classification uses history and confirmation; raw Stable can coexist with stabilized Growing when growth remains above the lower threshold.
7. All configuration interventions restart trend history conservatively. A change recorded on Day N first affects Day N+1 (zero-based snapshot.Day N). Minimum-history and confirmation state reset with that boundary. Session restore recomputes from recorded history.
8. GameSceneState and SimulationInsights attach the same `QueueTrend.From(live)` output. Insights priority/relevance still uses unchanged pressure classification. Historical Insights retain their original evidence/period, so historical and current observations should not be compared without checking dates.
9. Game View summary and station details use QueueTrends; ordinary sprite labels use that same trend. Blocked/constrained/batching/dependency badges retain their existing pressure-warning priority; those warnings are not competing trend calculations. No pressure rule changed.
10. Insights queue charts retain their separate four-day pressure-evidence window; trend evidence explicitly displays its own up-to-ten-day period.

## Deterministic scenario

Seed 12345, continuous arrivals 0.4 items/day, initially zero items. Other request settings are defaults except one tester and Testing effort 5: five developers, one unit capacity/person/day, Development effort 5, Review effort 1, WIP 5/3/3. No interventions. All history is generated by the unchanged simulator.

At Day 70, Days 61–70 contain 10 observations, queue endpoints 9→11, slope +0.2 items/day and fitted change +1.8. Entry=2, retention=1. The old high-entry gate rejects 1.8 even though neighboring windows periodically establish a strong growth candidate.

## Minimal correction

Numeric thresholds, rolling window, OLS and minimum sample count are unchanged. The FIRST window must still exceed the high entry threshold. The SECOND confirms that candidate if it supports the SAME direction above the lower retention threshold. A contrary/below-retention or insufficient window clears that candidate. An established direction continues using the existing lower retention rule. Confirmations are capped at two for diagnostics. No independent smoothing, longer window or KPI calculation was added.

This is an asymmetric entry/confirmation band, rather than arbitrarily lowering the entry threshold. A single-item step still cannot initiate a direction. Alternating noise at amplitudes 1, 2, 10 and 100 remains Stable. Adding offsets of 1,000 or 1,000,000 items gives the same direction; the mirrored reproduced history becomes Shrinking. True reversal and flattening clear the old direction.

## Remaining uncertainty

The exact user session was not provided. This fixed-seed reproduction matches the reported day/count/status and demonstrates a concrete algorithm defect, but cannot exclude a recent intervention, different observation period or other settings in the original run. Very small/unclear changes can still legitimately be Stable under the unchanged ten-day noise/quantization rule. Four-day pressure classifications can differ from ten-day queue direction; the UI now exposes the actual periods and calculations rather than implying they are equivalent.
